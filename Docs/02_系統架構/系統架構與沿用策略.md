# 系統架構與沿用策略

## 結論

建立新的小型 SwiftUI Universal App，不直接複製 Taiwan_Wtsbot 整套專案。沿用其已驗證的產品邏輯與測試觀念，重新實作離線所需的最小集合，避免把會員、伺服器、商務與遠端內容生命週期一併帶入。

## 目標模組

```text
3TcraneApp
├── AppShell             # iPhone Tab / iPad Sidebar
├── Features
│   ├── Home
│   ├── Learn
│   ├── CourseReview

│   ├── WrongBook

│   ├── LearningRecordRepository
│   └── PersistenceMigration

    ├── ColorTokens
    ├── Typography
    └── Components
```

## Taiwan_Wtsbot 借鏡矩陣

| 參考能力 | 決策 | 本專案作法 |
| --- | --- | --- |
| SwiftUI iPhone／iPad 雙導覽 | 借鏡 | TabView + NavigationSplitView，共用 feature views |
| 題庫穩定 ID 與 package schema | 簡化沿用 | 單一 bundle JSON，無 full/delta/下載流程 |
| 答案／解析／另外解答／來源分層 | 沿用 | 保留獨立欄位與 UI section |
| 閱讀式複習與作答式測驗分流 | 沿用 | CourseReview 直接顯示治理後答案內容；Practice 選答後才顯示；Exam 交卷後才顯示 |
| 錯題、作答、模擬考紀錄 | 沿用產品邏輯 | 以 SwiftData 小模型重作，不複製大型 OfflineStore |
| App／內容版本分離 | 沿用 | About 顯示兩者；內容仍只能隨 App 更新 |
| 升級、last-known-good 與資料保護 QA | 沿用 | 針對 UserStore migration 與 bundle content compatibility |
| 會員、登入、裝置 session | 不沿用 | MVP 無帳號 |
| API、Web、Bot、內容下載／delta | 不沿用 | 完全離線、無 server |
| StoreKit／訂閱／付費牆 | 不沿用 | 首版無內購 |
| Widget、社群、Android | 不沿用 | 控制範圍與測試量 |

## 技術決策

- SwiftUI、Swift concurrency、SwiftData；deployment target 17.0。
- 題庫 JSON 放 App bundle 並以 `Codable` 解析；bundle 是只讀內容權威。
- 使用者資料放 Application Support 的 SwiftData store，不能與題庫同檔。
- 不加入第三方套件；搜尋先以正規化字串＋記憶體 index，實測不足再考慮 SQLite FTS。
- 依賴注入 `QuestionRepository`／`LearningRecordRepository`，測試使用合成 fixture 與 temporary store。
- 無網路 entitlement、無背景下載；外部來源連結由使用者點擊才交給系統瀏覽器。

## 學習狀態機

```text
課程入口 → 科目／工作項目 → 閱讀式複習 → 前後題／跳題／繼續上次
                                      └→ 收藏／筆記

題庫入口 → 全部／工作項目／錯題 → 選答 → 判定 → 答案／解析／來源
                                      └→ 作答紀錄／錯題狀態

模擬測驗 → 抽題／計時 → 未交卷快照 → 交卷 → 成績／逐題檢討
```

`CourseReview` 只更新最後閱讀位置，不建立答對／答錯紀錄；`Practice` 與 `Exam` 才能更新 `QuestionProgress`。因此閱讀進度與測驗正確率不會互相污染。

## App 更新相容規則

- 題庫 item 必須容忍新增 optional 欄位。
- UserStore schema migration 只可 additive 或明確 staged migration。
- 舊 question ID 不可重用；缺題時顯示已下架狀態，不刪除紀錄。
- App 啟動先開 UserStore，再載入新 bundle；內容解析失敗時顯示安全錯誤，不重建 UserStore。

## 最小開發量控制

首版不拆成多個 Swift Package、不導入 Redux/Clean Architecture 框架、不建立後端。Feature 檔案在超過可維護門檻後再拆；資料邊界與 repository protocol 先保留，確保未來可替換而不提前建造未使用的基礎設施。
